# API платежей Квитто

Самостоятельная реализация тестового задания Junior Python / FastAPI.
Сервис хранит платежи, рассчитывает скидку и рассрочку и принимает изменение
статуса от банка. Реального списания денег нет.

## Запуск

Нужны Python 3.11+ и SQLite 3.35+ (обычно входит в Python). Проверено локально
на Python 3.12.10 / SQLite 3.49.1. Команды выполняются из корня репозитория.

```bash
python -m venv .venv
```

Активируйте окружение:

```powershell
# Windows PowerShell
.venv\Scripts\Activate.ps1
```

```bash
# Linux / macOS
source .venv/bin/activate
```

Если политика PowerShell запрещает активацию, вместо `python` используйте
`.venv\Scripts\python.exe` во всех дальнейших командах.

```bash
python -m pip install -r requirements-dev.txt
python -m uvicorn app.main:app --reload
```

Сервер: <http://127.0.0.1:8000>. Swagger UI: <http://127.0.0.1:8000/docs>.
OpenAPI: <http://127.0.0.1:8000/openapi.json>.
При старте Alembic применяет миграции, затем создаются три тарифа без дубликатов:
`basic` — 990000, `standard` — 1990000, `premium` — 2990000 копеек.
База `payments.db` сохраняется в текущем каталоге.

Для запуска без инструментов разработки достаточно `requirements.txt`.
Версии прямых зависимостей зафиксированы. Starlette и AnyIO тоже закреплены,
чтобы TestClient работал с требуемым заданием httpx без предупреждений
несовместимости. Это не полный lock-файл всех транзитивных зависимостей.

## Проверки

```bash
python -m pip check
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
```

Каждый тест получает отдельную файловую SQLite-БД в каталоге pytest `tmp_path`.
Каждый запуск использует новый временный каталог `kvitto-pytest-*`, который
удаляется после завершения. Это исключает конфликт прав Windows, когда
обычный терминал и изолированный ИИ-ассистент используют общий `pytest-of-<user>`.
Общий кеш `.pytest_cache` отключён по той же причине; команды `--lf` и `--ff`
не используются. Явно переданный `--basetemp` сохраняет обычное поведение pytest
и позволяет оставить файлы для разбора ошибок. Автоматический временный каталог
удаляется и при падении тестов.
Тесты применяют настоящие миграции; рабочая БД не используется.
Проверяются суммы, поля ответов и состояние БД, все 16 пар статусов, повторные
запросы, HMAC, rollback, перезапуск, совпадение миграции с моделями и гонки.
В тесте гонки шесть запросов выполняют предварительный SELECT до первой
вставки; ожидаются одна запись, один 201 и пять 200. Этот сценарий проверяется
и с транзакционными SELECT, и в стандартном режиме sqlite3.

## HTTP-контракт

| Маршрут | Результат |
| --- | --- |
| `GET /tariffs` | 200, список `{id, title, price}` |
| `POST /payments` | 201, новый платёж; 200 при повторе ключа |
| `GET /payments/{id}` | 200, платёж; 404 при отсутствии |
| `POST /webhooks/bank` | 200 `{"result":"ok"}`, 404 или 409 |
| `GET /payments` | 200, список; необязательные фильтры `email`, `status` |

Ответ платежа содержит ровно поля `id`, `status`, `tariff_id`, `amount`,
`discount`, `method`, `installment_months`, `schedule`, `email`, `created_at`.
`discount` — сумма скидки в копейках; `amount` — сумма к оплате после скидки.
`created_at` — дата создания в UTC в формате ISO 8601.
У card и sbp поля `installment_months` и `schedule` равны `null`.
У installment срок обязателен: целое число 3, 6 или 12.
Срок для card/sbp запрещён; явно переданный `null` допустим.

Ошибки Pydantic сохраняют стандартный формат FastAPI 422 с массивом `detail`.
Неизвестный тариф возвращает 404 `{"detail":"Tariff not found"}`.
Неизвестный платёж возвращает 404 `{"detail":"Payment not found"}`.
Неизвестные поля тела запрещены. ID — положительное целое до `2**63 - 1`;
строки, дроби и boolean в ID тела запроса не принимаются.

## Примеры curl

Примеры рассчитаны на Bash / Git Bash / WSL. ID тарифа и платежа берите из
ответов сервера; на новой БД standard обычно имеет ID 2, первый платёж — ID 1.

```bash
curl -s http://127.0.0.1:8000/tariffs

curl -i http://127.0.0.1:8000/payments \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: order-001' \
  -d '{"tariff_id":2,"email":"student@example.com","method":"card","promo_code":"kvitto10"}'

# Повтор предыдущей команды вернёт тот же платёж с HTTP 200.
curl -i http://127.0.0.1:8000/payments \
  -H 'Content-Type: application/json' \
  -d '{"tariff_id":2,"email":"student@example.com","method":"installment","installment_months":3}'

curl -s http://127.0.0.1:8000/payments/1

curl -i http://127.0.0.1:8000/webhooks/bank \
  -H 'Content-Type: application/json' \
  -d '{"payment_id":1,"status":"succeeded"}'

curl -s 'http://127.0.0.1:8000/payments?email=student%40example.com&status=succeeded'
```

В PowerShell можно передать тело через файл, избегая различий экранирования:

```powershell
'{"tariff_id":2,"email":"student@example.com","method":"sbp"}' | Set-Content -Encoding ascii request.json
curl.exe -i http://127.0.0.1:8000/payments -H "Content-Type: application/json" --data-binary "@request.json"
```

## Деньги и рассрочка

Все денежные значения в Python, API и БД — целые копейки. Float и Decimal
для денежных вычислений не нужны: единственная скидка равна 10%.
Для положительной цены скидка рассчитывается как `(price + 5) // 10`.
Это округление до ближайшей копейки, при половине — вверх (half up).
Итог `amount = price - discount`, поэтому копейки не теряются и не возникают.
Например, для 105 копеек скидка 11, к оплате 94. Для standard с промокодом
скидка 199000, к оплате 1791000 копеек.

`KVITTO10` принимается в любом регистре. Пустая строка, пробелы вокруг кода
и неизвестный код дают 422; отсутствие или `null` означает отсутствие скидки.

График строится через `part, remainder = divmod(amount, months)`.
Первые `remainder` платежей равны `part + 1`, остальные — `part`.
Пример из PDF: 1990000 / 3 → `[663334, 663333, 663333]`.
График вычисляется из сохранённых суммы и срока: изменение цены тарифа
не меняет уже созданный платёж. Даты платежей не нужны по заданию.

## Идемпотентность и транзакции

`Idempotency-Key` необязателен. Допустимы 1–255 печатных ASCII-символов без
пробелов; регистр ключа важен. Без ключа одинаковые запросы создают разные
платежи. Ключ уникален для всего сервиса и хранится без срока удаления.

Сохранён SHA-256 от канонического JSON после валидации. Порядок полей,
регистр промокода и отсутствие необязательного поля вместо `null` не меняют
смысл запроса. Email нормализуется EmailStr: домен приводится к нижнему
регистру, регистр локальной части сохраняется. Фильтр email сравнивает
нормализованное значение точно.

Повтор того же запроса возвращает существующий ресурс с HTTP 200, исходными
денежными значениями и его **текущим** статусом. Повтор ключа с другими
валидными параметрами возвращает 409 `{"error":"idempotency_conflict"}`.
Исходная запись не меняется. Невалидное тело сначала получает обычный 422.

Предварительный SELECT ускоряет обычный повтор, но защита находится в БД:
UNIQUE и `INSERT ... ON CONFLICT(idempotency_key) DO NOTHING RETURNING id`.
При гонке победитель вставляет запись, остальные читают её и сверяют хеш.
Игнорируется только конфликт указанного ключа; остальные ошибки БД не скрываются.
`session.begin()` делает commit при успехе и rollback при исключении,
зависимость FastAPI закрывает сессию после запроса.

Чтение тарифа завершается до транзакции вставки. Это не даёт SQLite повышать
устаревший снимок чтения до записи после конкурентного commit. Цена фиксируется
в момент чтения; маршрутов изменения тарифов нет. Запись самого платежа атомарна.

## Статусы и вебхуки

Разрешены только `pending → succeeded`, `pending → failed`,
`succeeded → refunded`. Новый платёж — pending.
Запрещённый переход, включая повтор того же статуса, возвращает строго
409 `{"error":"invalid_transition"}` и ничего не меняет.
Обновление выполняется одним `UPDATE ... WHERE id = ... AND status = ...`.
Два конкурирующих вебхука succeeded/failed не могут оба изменить pending.

Если `WEBHOOK_SECRET` отсутствует или пуст, подпись не проверяется:
обязательные сценарии задания работают без дополнительной настройки.
Если секрет задан, нужен `X-Signature`: 64 символа lowercase hex от
HMAC-SHA256 **исходных байтов** тела. Префикс `sha256=` не используется.
Сравнение — `hmac.compare_digest`; неверная или отсутствующая подпись даёт 401.
HMAC подтверждает подлинность и целостность, но сам по себе не защищает от
повторной доставки; повторный статус ограничен правилами переходов.

Переменные окружения читаются при создании приложения. `.env` автоматически
читает Docker Compose; для обычного Python-запуска переменные нужно экспортировать.

```powershell
$env:WEBHOOK_SECRET = "your-local-secret"
python -m uvicorn app.main:app --reload
```

Подписанный запрос (Bash; секрет должен совпадать с сервером):

```bash
export WEBHOOK_SECRET='your-local-secret'
printf '%s' '{"payment_id":1,"status":"succeeded"}' > webhook.json
SIGNATURE=$(python -c 'import hashlib,hmac,os,pathlib; print(hmac.new(os.environ["WEBHOOK_SECRET"].encode(), pathlib.Path("webhook.json").read_bytes(), hashlib.sha256).hexdigest())')
curl -i http://127.0.0.1:8000/webhooks/bank \
  -H 'Content-Type: application/json' \
  -H "X-Signature: $SIGNATURE" --data-binary @webhook.json
```

## Docker и миграции

```bash
docker compose up --build
docker compose down
```

После первой сборки достаточно `docker compose up`. База хранится в именованном
томе `payment-data` и переживает `down`. Контейнер работает без root.
В этой среде Docker недоступен, поэтому сборка и Compose не запускались.

`DATABASE_URL` по умолчанию — `sqlite:///./payments.db`, в контейнере —
`sqlite:////data/payments.db`. Родительский каталог файла должен существовать.
Используется файловая SQLite; PostgreSQL и in-memory режим не поддерживаются.

Миграции запускаются автоматически при старте, но доступны и вручную:

```bash
python -m alembic upgrade head
python -m alembic current
python -m alembic check
# При изменении моделей:
python -m alembic revision --autogenerate -m "describe schema change"
```

Новая миграция требует ревью перед применением. Тарифы создаются при старте
приложения, а не командой `alembic upgrade`. Не используйте `create_all` вместе
с миграциями. Одновременный первый старт нескольких процессов не рассчитан
на гонку применения миграций: для этого проекта используйте один worker.

## Структура и ограничения

- `app/api.py` — HTTP, сессия запроса, подпись, преобразование бизнес-ошибок.
- `app/schemas.py` — Pydantic v2: входные данные и точный формат ответа.
- `app/models.py` — SQLAlchemy 2.x: таблицы, ограничения, вычисляемый график.
- `app/services.py` — создание платежа, идемпотентность, переходы статусов.
- `app/money.py` — целочисленные вычисления без обращения к БД.
- `app/db.py` — движок, Alembic и начальные тарифы.
- `app/config.py`, `app/main.py` — настройки и жизненный цикл приложения.
- `migrations/`, `tests/` — история схемы и независимые проверки.
- `AI_LOG.md`, `REVIEW.md`, `AGENTS.md` — использование ИИ и проверка решения.

Обработчики `def` используют синхронную SQLAlchemy в пуле потоков FastAPI.
`async def` нужен для чтения исходного HTTP-тела и жизненного цикла; блокирующая
инициализация БД вынесена в пул потоков.

SQLite допускает одного писателя одновременно. WAL улучшает совместимость
чтения и записи; ожидание блокировки ограничено 10 секундами. При долгой
внешней блокировке возможна ошибка БД/HTTP 500; автоматических повторов нет.
UNIQUE предотвращает дубликаты, но это не обещание успешности при любой нагрузке.
Для production нужны PostgreSQL, отдельный запуск миграций, наблюдаемость,
пагинация списка, политика хранения ключей и полноценный протокол банка.
Авторизация, фронтенд и реальный банк исключены из объёма задания.

GitHub Actions настроен на Ruff и pytest для Python 3.11, 3.12 и 3.13.
Фактический удалённый запуск нужно проверить после публикации репозитория.
